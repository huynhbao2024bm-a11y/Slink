# Backend foundation — setup notes

**Purpose:** Explain the backend foundation and its safety boundary so local setup is reproducible without mistaking the current API shell for a customer-ready service.

## Current state

- `server/migrations/0001_core.sql` defines tenant-scoped PostgreSQL records, row-level security, and append-only stock/financial/audit history.
- `server/migrations/0002_store_profile.sql` adds versioned store contact and receipt-footer fields for server-backed settings.
- `server/migrations/0003_password_recovery.sql` adds expiring, single-use password-reset tokens.
- `server/migrations/0004_export_lookup_indexes.sql` adds store/date indexes used by bounded exports and their date filters.
- `server/migrations/0005_cash_tender_history.sql` stores cash received and change on each order, and backfills historical cash receipt from successful cash payment rows. Earlier change values were not recorded, so those historical rows remain zero for change rather than inventing values.
- `server/migrations/0006_store_invitations.sql` adds hashed, expiring store invitations with pending-account claims and row-level policies for owner and invitee flows.
- `server/migrations/0007_cash_register_sessions.sql` adds one active cash-register session per store, opening float, counted closing cash and variance, and an optional session link on cash movements.
- Migrations `0010_purchase_orders.sql` through `0014_membership_warehouse_scopes.sql` add versioned supplier orders/receipts, warehouse-scoped inventory/transfers, explicit restock destinations, and tenant-scoped stockkeeper warehouse permissions. Migrations 0012–0013 backfill historical records to their original order warehouse; new return/void operations validate an active destination. `0015_order_notes_tags.sql` adds append-only, RLS-protected internal order notes and tag-change history. `0016_customer_tags.sql` adds append-only, RLS-protected customer tag history for CRM classification and filtering.
- `server/migrate.js` serializes migration runs with an advisory lock, stores a checksum for each applied file, refuses to run an edited migration as if it were new, and grants the existing `slink_app` role the table/sequence privileges used by the API. It then removes access to `schema_migrations` and restricts account-security events and append-only order note/tag/customer-tag history to SELECT/INSERT. Create both roles before running it; migrations fail clearly if `slink_app` is missing.
- `server/db.js` exposes an application pool and transaction helpers that set user/store context and check active store membership before business queries.
- `server/index.js` serves only an allowlist of Slink assets, adds security headers, and exposes liveness/readiness endpoints.
- Production startup and migrations require `PG_SSL=true`; the PostgreSQL client verifies the server certificate instead of silently falling back to plaintext or trusting any certificate.
- API request logs use the matched route template, response status and duration rather than raw URLs; Fastify's `LogController` suppresses automatic request logging for API and query-string URLs so customer searches and token links do not enter application access logs as raw URL values.
- `server/auth.js` provides account registration, email verification, password recovery, sign-in/out, current-session, store-listing, opaque database-backed sessions, and same-origin/CSRF checks. Email delivery does not follow redirects. Development without an email delivery endpoint returns verification and reset links through API responses; production refuses to start unless an HTTPS public origin and authenticated HTTPS email-delivery endpoint are configured.
- `server/staff.js` provides owner-only staff listing, email invitations, invite-based account creation, acceptance after verified email, resend/revoke, role updates, suspension/reactivation and audit events. Development returns the invitation URL; production relies on the configured email provider. The migration runner grants application access to migrated workflow tables.
- `server/cash-register.js` opens and closes store cash sessions. Cash sales/change, cash refunds, debt collections, supplier payments, purchase payments and manual cashbook movements require an active session and carry its ID. Non-cash tender is excluded from expected drawer cash. A close records counted cash; a nonzero discrepancy requires a reason and creates a cashbook adjustment and audit event in the same transaction. Only one session may be open per store; a cashier may close only their own session. The migration runner grants application access to migrated workflow tables.
- `GET /api/stores/:storeId/cash-register` returns the active session and the 10 most recently closed sessions. Cashiers receive their own closed sessions; owners, managers, and accountants can view store-wide history. The Finance UI shows the session open/close actors, reconciliation totals, variance and reason. Cashbook rows show the recording actor and session association; the CSV export includes session ID and opening time.
- Finance read routes are role-scoped: owners, managers, and accountants receive financial totals, debtors, payables, cashbook and analytics; cashiers receive current/their-own cash-session ledger rows; stockkeepers receive supplier names and purchase records for receiving but no cashbook, debt totals or analytics. The browser hides financial dashboard metrics and reports for cashier/stockkeeper roles. This boundary has only received static code review so far and still requires per-role API acceptance.
- `server/products.js` provides authenticated, store-scoped catalog listing/search, create, version-checked update, and archive. Catalog mutations are transactional and write audit/cost history.
- Product search/list responses, inventory rows, stock valuation summaries, and order-line detail omit cost values for cashiers. Customer and order history endpoints deny the stockkeeper role; their list queries also filter explicitly by store ID in addition to row-level security. The browser hides POS, orders and customer areas from stockkeepers and POS from accountants.
- `server/sales.js`, `server/returns.js`, `server/payments.js`, `server/stock.js`, `server/purchases.js`, `server/purchase-orders.js`, `server/warehouses.js`, `server/finance.js`, `server/analytics.js`, and `server/records.js` expose transactional retail workflows with store scoping, role checks, idempotency for retried writes, stock/order/warehouse locks, audit events, and ledger entries. Local PGlite acceptance includes split tender, non-cash overpayment rejection, changed-key payload conflict, unpaid-order void and replay, archived sale-warehouse rejection with safe void-to-active-warehouse retry, cross-warehouse return with archived-source rejection/safe retry, plus an insufficient-stock rollback/retry. Payment providers are not connected, so payment amounts are operator-recorded confirmations.
- Customer onboarding can create an opening receivable ledger debit; supplier onboarding can create or reuse a supplier and record an opening payable. Both operations use idempotency and audit records, and opening balances do not create cash movements. Only owners, managers, and accountants can record an opening balance.
- The browser client has registration, sign-in, email verification, password reset, session restoration, sign-out, a searchable server-backed catalog and connected POS, order detail/returns, customer records, inventory adjustment, purchase receiving/history/details, supplier payment, cash movements, analytics, version-checked store profile settings, and an owner-only staff invitation/role screen.
- `server/exports.js` provides authenticated store-scoped CSV downloads for catalog/inventory snapshots and movement history, customer/supplier profiles and ledgers, orders and order lines, payments, returns/refunds, cashbook, and purchases. It limits finance/customer exports to owner, manager, and accountant roles, and stock/purchase exports to owner, manager, stockkeeper, and accountant roles. Each successful export is audited. It exports up to 50,000 rows per file, supports inclusive store-time-zone date ranges, preserves VND as integer text, and rejects oversized exports instead of returning partial data. All 14 datasets returned 200 with a UTF-8 BOM on the local PGlite role; native PostgreSQL, authorization/date/row-limit boundaries and phone downloads remain unverified.
- The browser exposes the CSV export dialog from the products, orders, customers, inventory, and finance screens. Export files come from the server rather than the loaded list page; this is a data export workflow, not a database backup or restore procedure.
- Checkout accepts up to five distinct tender methods, records each applied payment, writes actual incoming cash plus a separate change outflow, and persists the cash received/change amounts on the order. Non-cash tender cannot exceed the order total. Single-method pending requests retain their prior idempotency hash so an in-flight sale can still be retried after the client update. Split cash/bank-transfer, same-key replay, changed-payload conflict, and non-cash overpayment rejection passed on local PGlite; native PostgreSQL and device acceptance remain open.
- Owners and managers can void an unpaid, unreturned order with a required reason and explicit confirmation that goods were not delivered or are back in the store. The server locks the order, restores only stock movements recorded by that sale, writes customer-ledger and stock reversal entries, updates the order status, and audits the reason in one transaction. Local PGlite accepted the confirmation requirement, inventory/debt reversal and repeated-void no-op. Orders with any payment must use return/refund handling; native PostgreSQL and device acceptance remain open.
- Product/customer/order list APIs are paginated. The POS and purchase pickers search the full active catalog through the API rather than only searching the first loaded page.
- Product CSV onboarding imports up to 200 products with optional opening stock in one transaction after client preview and server validation; customer opening receivables and supplier opening payables are ledger entries and do not create cash movements. These flows have local PGlite API evidence, but browser file selection, reload recovery and native PostgreSQL acceptance remain open.

## Local development runtime

- `pnpm dev` starts the same Fastify API and PWA with PGlite, using the real migration files and a non-owner `slink_app` role for application transactions. PGlite runs in one process and serializes local requests; it is only a convenient local development runtime. The app-shell service worker uses network-first requests with the cached shell as its offline fallback.
- The database persists in `.local-data/pglite` by default. Set `SLINK_LOCAL_DATA_DIR` to use another local folder. This path is ignored by Git and contains business data; keep it private and back it up before deleting or moving it.
- On this Windows development machine, a native PostgreSQL 18 cluster persists in `.local-data/postgres-native` and listens only on `127.0.0.1:5433`. The one-time setup created distinct random `slink_migrator` and `slink_app` credentials in the ignored, ACL-restricted `.env`; the app role is intended to be a non-superuser with `NOBYPASSRLS`, no schema `CREATE` privilege and no read access to `schema_migrations`. The PostgreSQL administrator secret is DPAPI-encrypted under the current Windows account. Use `pnpm db:postgres:start`, `pnpm db:postgres:status`, and `pnpm db:postgres:stop` to manage this cluster; `pnpm start:native` starts the cluster and Fastify together. Run `pnpm db:postgres:check-role` after migrations to verify application-role flags, inherited privileges, relation ownership, migration-ledger denial, and the account-security table grants/RLS (or run `node scripts/postgres-role-check.js` where pnpm is unavailable). This is local development infrastructure, not a managed production deployment.
- When `pnpm` is unavailable in PowerShell, `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\start-native-local.ps1` starts the local PostgreSQL cluster and then runs the API in the foreground. It requires Node.js 24.11+ in major version 24, checks `/api/ready` before starting another API, waits for an existing Slink server to reconnect, and does not stop an unrelated process occupying port 3000. Press Ctrl+C to stop the foreground API; PostgreSQL remains running.
- To accept the current native schema and core transaction path without changing the real `slink` database or stopping the open API, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\postgres-native-acceptance.ps1` from `D:\Slink`. The helper verifies the protected local role URLs and PostgreSQL 18 cluster identity, uses the same-Windows-user DPAPI administrator credential without displaying it, creates a randomly named `slink_accept_*` database, applies the source migrations, checks role boundaries, and runs synthetic registration, cross-store isolation, import/opening stock, sale/retry/oversell, return/refund, concurrent sales, bulk inventory count, purchases, debt settlements, cash reconciliation and CSV flows through the API and `slink_app` role. It drops only that generated database even after a failed acceptance; if cleanup itself fails it prints the exact temporary database name. It reports failures at the first failing step. The synthetic accounts use the reserved `.invalid` domain and no email is sent. The opt-in `-IncludeBackupRestore` variant also creates and verifies an encrypted backup of the synthetic database, restores it into a separate `template0` database, compares every public table and sequence, reruns migration/role checks, authenticates the restored synthetic account and reads its catalog with `slink_app`; both generated databases and the unique encrypted test artifact are removed in `finally`. Run it with `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\postgres-native-acceptance.ps1 -IncludeBackupRestore`. This is local native evidence, not managed-production or physical-device acceptance. pnpm aliases are `db:postgres:acceptance` and `db:postgres:acceptance:restore` where pnpm is installed.
- `node scripts/postgres-app-preflight.js` verifies that the protected `APP_DATABASE_URL` can connect as `slink_app` and run a read-only query. It refuses non-loopback hosts, another role, or another database, and prints no credential. Migration-role checks alone do not verify the API's actual database login.
- To rotate the local `postgres` administrator password without exposing the current or new password in chat, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\postgres-admin-rotate.ps1` from `D:\Slink` as the same Windows user. It uses the DPAPI-protected current credential, prompts twice for the new password without echo, updates the local database and the DPAPI file, and does not change `slink_app` or `slink_migrator` passwords.
- If rotation leaves `.local-data\postgres-admin.dpapi.pending`, do not delete or overwrite it manually. With PostgreSQL running, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\postgres-admin-recover-pending.ps1`. The helper checks both DPAPI-protected credentials against a read-only localhost query, then promotes the accepted pending credential or removes it only after confirming the saved credential works. If neither is accepted, both files remain for controlled password recovery.
- If neither saved credential works, `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\postgres-admin-reset-local.ps1` performs a verified, offline physical backup of the PostgreSQL 18 cluster under `D:\Slink-postgres-backups`, applies a temporary `trust` rule for the `postgres` role on IPv4 loopback only, opens `psql` so the operator can run `\password postgres`, restores the original `pg_hba.conf`, restarts normally, verifies the new password, and updates the same-user DPAPI credential. Stop the Slink API on port 3000 first. This targets the Slink data directory on port 5433; the separate Windows service on port 5432 is not the Slink cluster. The physical backup is for the same PostgreSQL major version and is not a `pg_restore` archive.
- If password verification succeeded but the reset script was interrupted while promoting its DPAPI file, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\postgres-admin-finish-reset.ps1`. It rechecks the encrypted temporary credential against PostgreSQL before replacing the saved credential and preserves the old encrypted file.
- After the local administrator credential is usable, the authorized migration-role repair is `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\postgres-admin-repair-migration-role.ps1`. It grants only `BYPASSRLS` and `CREATE` on `public` to the non-superuser `slink_migrator`, verifies those flags, and does not run migrations or change the `slink_app` credential.
- `server/import-pglite-to-postgres.js` supports an explicit one-time local import from a **copy** of a PGlite data directory. It refuses production mode, a non-local PostgreSQL target, the original `.local-data/pglite` path, a missing account-verification email, or a destination that already contains business rows. It imports compatible columns in a single transaction; migrations stay managed by the native target. ## Connection roles

Use separate PostgreSQL credentials:

- **Migration role:** a dedicated, non-superuser `slink_migrator` with `BYPASSRLS` for tenant-wide historical backfills and `CREATE` on `public`. This privilege is limited to the release/migration identity; never grant it to `slink_app`.
- **Application role:** non-superuser, `NOBYPASSRLS`, does not own the tables, and only has the data privileges needed by the API. It must not be able to create/alter schema or read `schema_migrations`.

The application must use `APP_DATABASE_URL`; migration tooling must use `MIGRATION_DATABASE_URL`. Create both roles before migration. `server/migrate.js` now verifies that the connection is `slink_migrator`, that it is not a superuser, has `BYPASSRLS` and can create in `public`, and that `slink_app` exists before it applies any migration. After a successful migration run, it applies table and sequence grants, denies access to `schema_migrations`, and keeps account-security events append-only for the app role. Run `node scripts/postgres-role-check.js` as a post-migration release check. Do not reuse a superuser connection for the running API, because superusers bypass row-level security. The repository does not contain database credentials.

## Local environment

1. Install dependencies with the project package manager.
2. Create a PostgreSQL database and the two roles above; do not use production data during development.
3. Copy `.env.example` to `.env` and replace the placeholder connection strings with local development credentials. Never commit `.env`.
4. For local development, registration returns a verification link because no mail provider is required. For production, configure `PUBLIC_ORIGIN` to the HTTPS site origin, `EMAIL_DELIVERY_URL` to an HTTPS endpoint that accepts JSON `{ "to", "subject", "text" }`, and `EMAIL_DELIVERY_TOKEN` as its Bearer credential. The delivery endpoint must return a 2xx response only after accepting the message. Do not expose the development verification-link behavior in production.
5. Run the migration command, then start the server. `GET /api/health` reports process liveness; `GET /api/ready` reports database connectivity.
6. The current API checks use PGlite with a non-owner `slink_app` role. PGlite validates migration SQL and basic tenant/constraint behavior; it is not a replacement for running the same migrations, role grants, and workflows against the selected native managed PostgreSQL service.

For the Slink-owned Windows PostgreSQL cluster only, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\postgres-backup-prepare-local.ps1` to create and verify an encrypted logical backup. Add `-ApplyMigrations` only when you intend to apply pending migrations: after the backup succeeds, the helper refuses to migrate while port 3000 has a listener; `server/migrate.js` checks the `slink_migrator` privileges and confirms `slink_app` exists before schema changes; then the helper runs the full table/RLS role check after migrations. Do not run the full role checker before migrations, because it requires tables introduced by the latest schema. When a backup was just verified, pass `-VerifiedBackupManifest 'D:\Slink\.local-data\backups\<manifest>.manifest.json'` with `-ApplyMigrations`; the helper restricts the path to the local backup directory and verifies the backup again before reusing it, avoiding a duplicate archive. The helper uses the existing local `slink_migrator` URL, requires `.env` to have a restricted ACL, and stores a random AES-256 key in that ignored file without printing it. This local helper does not configure production backup storage: production keys belong in a secret manager and backups must be copied to separate encrypted storage with a restore rehearsal.

## Deployment boundary

Production still needs an approved HTTPS domain, managed PostgreSQL, secret injection, backups/restore, monitoring, and a provider role setup. Set `PG_SSL=true` in every production environment; the PostgreSQL client verifies the certificate and rejects untrusted certificates. Configure the selected database service's CA trust through the supported Node.js certificate configuration if it uses a private CA. Set `TRUSTED_PROXY_IPS` only to the actual proxy address/CIDR; do not trust arbitrary forwarded headers.

The repository includes a non-root production container and a CI image-build job. See [`DEPLOYMENT.md`](DEPLOYMENT.md) for the release migration, health check, secret separation, backup, and rollback process. The image has not yet been built in this workspace because Docker is unavailable; CI must pass before treating the artifact as verified.

Do not expose this version to real customer data or describe it as ready to sell. Browser workflow verification beyond the tested screens, iOS/Android device verification, durable offline synchronization, domain acceptance verification, native PostgreSQL role and workflow evidence, backups/restore, privacy documents, monitoring, and release operations remain open in `DELIVERY_ROADMAP.md`. Production email delivery and the staff flow on native PostgreSQL still need provider and database acceptance.
